# Internationalization (i18n)

> Source: https://developer.salesforce.com/docs/commerce/pwa-kit-managed-runtime/guide/sfnext-intl.html

**Mental model:** i18next with dual instances (server has all translations; client dynamically imports per-language chunks). Locale detection by multisite middleware (runs before i18next). Language switch at runtime without page reload. Translation files in `src/locales/`.

## Quick Usage

```typescript
// React components
import { useTranslation } from 'react-i18next';
const { t } = useTranslation('product');
t('title')
t('greeting', { name: 'John' })  // interpolation
t('summary.itemsInCart', { count: 3 })  // pluralization

// Multiple namespaces
const { t } = useTranslation(['home', 'product']);
t('home:title')

// Server (loaders, actions)
import { getTranslation } from '@salesforce/storefront-next-runtime/i18n';
export function loader(args: LoaderFunctionArgs) {
  const { t } = getTranslation(args.context);
  return { title: t('product:title') };
}

// Client non-component code
const { t } = getTranslation();  // no context needed client-side
```

## Configuration

```typescript
// config.server.ts
i18n: {
  fallbackLng: 'en-GB',
  supportedLngs: ['it-IT', 'en-US', 'en-GB'],  // fallback language LAST
}
```

Must match `commerce.sites[].supportedLocales[].id` values. Each locale needs a directory in `src/locales/`.

## Architecture

- Server: has all translations, renders SSR with correct language
- Client: reads language from HTML `lang` attribute, dynamically imports ALL translations for that language as static JS chunk (CDN-cached, immutable)
- Subsequent requests use cached data; language switch loads new chunk if uncached

## Extension Translations

Extensions maintain own translations in `src/extensions/<name>/locales/<locale>/translations.json`. Auto-namespaced as `extMyExtension` (PascalCase of folder name).

```typescript
const { t } = useTranslation('extMyExtension');
```

## Currency System

Priority: User's manual selection (cookie) → Locale's preferred currency → Site's default currency.

## Zod Schema Factory Pattern (Critical)

Never create Zod schemas with `t()` at module level — race condition:

```typescript
// ❌ WRONG — Module-level schema (t() may not be initialized)
export const schema = z.object({
  email: z.string().email(t('validation:emailInvalid'))
});

// ✅ CORRECT — Factory function
import type { TFunction } from 'i18next';

export const createSchema = (t: TFunction) => {
  return z.object({
    email: z.string().email(t('validation:emailInvalid'))
  });
};

// Usage in component
function MyForm() {
  const { t } = useTranslation();
  const schema = useMemo(() => createSchema(t), [t]);
  const form = useForm({ resolver: zodResolver(schema) });
}
```

## Rules

- Always pass `context` to `getTranslation()` on server
- Never use `translation` as namespace (doesn't exist); always specify namespace explicitly
- Keep `i18n.supportedLngs` in sync with `commerce.sites[].supportedLocales`
- Each new language needs: entry in `supportedLngs`, entry in site's `supportedLocales`, translation directory
- Client chunk is loaded once per language — all namespaces included
- Never create Zod schemas with `t()` at module level — use factory pattern
